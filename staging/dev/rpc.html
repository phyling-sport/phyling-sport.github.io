API - Commandes (RPC)

API - Commandes (RPC)

Cette page détaille l'exécution de commandes RPC sur un device : envoi, lecture du résultat, codes d'erreur et commandes courantes. Elle complète API - Temps réel.

Les commandes device sont asynchrones et transitent par deux routes : on envoie la commande via /rpc/request (qui répond immédiatement), puis on récupère le résultat en interrogeant /rpc/response.

1. Envoyer la commande :

POST /devices/rt/{client_id}/{device_number}/rpc/request
Authorization: Bearer <access_token>
{
  "method": "v1.record.rec.start",
  "params": {}
}
  • method doit correspondre à une valeur listée dans settings.features. Exemple : settings.features.record.cmd_start contient la valeur "v1.record.rec.start" à utiliser dans method.
  • feature / cmd_type sont une syntaxe alternative : { "feature": "record", "cmd_type": "cmd_start" } est équivalent à { "method": "v1.record.rec.start" }.

La route répond toujours immédiatement :

  • 201 : la commande est en cours de traitement. La réponse contient l'id de la requête, à utiliser pour récupérer le résultat.
    { "message": "Command is being processed", "id": "3f2a1c9e-1b2c-4d5e-8f90-abcdef123456" }
  • 200 : la commande a un résultat immédiat (notification ou valeur en cache) — aucun polling nécessaire.

2. Récupérer le résultat :

POST /devices/rt/{client_id}/{device_number}/rpc/response
Authorization: Bearer <access_token>
{
  "id": "3f2a1c9e-1b2c-4d5e-8f90-abcdef123456"
}
  • 202 : la commande est toujours en cours de traitement — réessayez plus tard.
  • 200 (ou un code d'erreur mappé) : le résultat est disponible. Le polling est idempotent : le résultat reste consultable jusqu'à son expiration (quelques minutes après le timeout de la commande).
  • 404 : id inconnu ou expiré.

En pratique, on interroge /rpc/response une fois par seconde après le 201, jusqu'à obtenir un code différent de 202. Surveillez également app/device/{device}/board/status pour voir l'état fusionné avec vos settings locaux.

⏱️ Délai d'exécution (Phyling-Live). Sur un device en économie d'énergie, le résultat peut mettre jusqu'au timeout de la commande (4 s par défaut) plus rpc_link_allowance à devenir disponible : cette marge vaut mqtt_refresh_delay + 10 s quand le LTE du device est actif (le device ne se réveille qu'à intervalle mqtt_refresh_delay), et 0 sinon ; elle est indiquée dans le champ rpc_link_allowance de /settings, cf. API - Temps réel. Avec un intervalle de 10 s, le délai monte ainsi à 24 s. Une commande comme v1.record.rec.start/stop peut donc renvoyer 202 pendant plusieurs secondes ; au-delà, /rpc/response renvoie l'erreur -32003 (timeout). Pour un Maxi ou un Phyling-Live en WiFi seul, le délai reste de 4 s.

Codes d'erreur RPC

Chaque réponse RPC peut porter un objet error au lieu d'un result. Les codes suivent la spécification JSON-RPC 2.0 et sont étendus par des codes Phyling négatifs dans la plage -32000 à -32004.

CodeMessageSignification
Erreurs JSON-RPC standard
-32700Parse errorJSON invalide reçu par le serveur.
-32600Invalid RequestL'objet envoyé n'est pas une requête JSON-RPC valide.
-32601Method not foundLa méthode n'existe pas ou n'est pas disponible.
-32602Invalid paramsParamètre(s) invalide(s).
-32603Internal errorErreur interne JSON-RPC.
Erreurs Phyling
-32000Service unavailableMQTT déconnecté, device hors ligne, en cours d'extinction, etc.
-32001Record in progressLa méthode RPC ne peut pas être exécutée pendant un enregistrement, ou (calibration auto) tant que le device n'est pas à l'état idle ou idle_sleep ; aussi un état cible (state) inaccessible pour v1.board.profile.apply.
-32002Not recordingLa méthode RPC ne peut pas être exécutée en dehors d'un enregistrement.
-32003Request timeoutLa réponse du device n'est jamais arrivée dans le délai imparti.
-32004Max size reachedLe contenu dépasse la taille maximale acceptée.

L'objet error peut porter un champ data optionnel, quand le device a un détail exploitable à ajouter à son code d'erreur — typiquement une chaîne reason en snake_case, stable et destinée au code appelant, pas à l'affichage. Un error sans data reste la forme normale : ne pas en faire une condition.

RPC courants

Arrêt / Redémarrage — v1.board.shutdown · v1.board.restart

{ "method": "v1.board.shutdown" }
{ "method": "v1.board.restart" }

Résultat :

{ "actions": ["shutdown"] }
{ "actions": ["restart"] }

Erreurs possibles : -32000 (service unavailable), -32001 (record en cours), -32003 (timeout).

Un enregistrement en cours bloque l'arrêt/redémarrage. Stoppez d'abord l'enregistrement via v1.record.rec.stop.

Lire un fichier — v1.board.<elem>.get

<elem> peut être : config, calib, wifi, device_info.

{ "method": "v1.board.config.get" }

Résultat :

{ "content": { /* contenu JSON du fichier */ } }

Erreurs possibles : -32000, -32003.

Écrire un fichier — v1.board.<elem>.set

<elem> peut être : config, calib, wifi, device_info.

{
  "method": "v1.board.config.set",
  "params": { "content": { /* contenu JSON complet */ } }
}

Variantes par élément :

ÉlémentVariante paramsEffet
calib{ "merge_calib": { … } }Fusionne partiellement avec la calibration existante (ajout module, update factor…)

Résultat : { "actions": ["restart"] } (sauf pour calib qui ne redémarre pas).

Erreurs possibles : -32000, -32001 (record en cours), -32602 (params invalides), -32003.

Changer de point d'accès WiFi — v1.board.wifi.connect

📡 Maxi et Phyling-Live (firmware ≥ v7.0.6). La commande est disponible quand le device déclare la clé wifi_connect dans features (voir API - Temps réel) ; les autres firmwares ne la déclarent pas et répondent -32601.

Demande au capteur de quitter immédiatement sa borne actuelle, sans attendre que les conditions habituelles (marge de gain, seuils de RSSI, délai entre deux bascules) soient réunies. Utile pour dégager un capteur collé à une borne saturée, et pour rejouer un essai de roaming sans dépendre des conditions radio.

Trois formes, selon les paramètres fournis :

ParamètreEffet
(aucun)Le capteur lance un scan complet, puis se connecte à la borne au meilleur RSSI.
ssidSSID d'un réseau activé de la configuration du device. Le capteur se connecte à la meilleure autre borne de ce SSID présente dans sa table de voisinage.
bssidAdresse MAC d'une borne, au format xx:xx:xx:xx:xx:xx. Le capteur s'y connecte si elle est présente dans sa table de voisinage.

Fournir ssid et bssid à la fois est une erreur de paramètres.

Dans les trois formes, être déjà sur la borne demandée est un succès, pas un refus : le capteur ne bouge pas, aucune coupure n'a lieu, et la réponse le dit avec changed: false. La question « suis-je sur la bonne borne ? » se lit donc sur le code de retour, et changed dit seulement s'il a fallu bouger pour y être.

{ "method": "v1.board.wifi.connect" }
{ "method": "v1.board.wifi.connect", "params": { "ssid": "Phyling-Stade" } }
{ "method": "v1.board.wifi.connect", "params": { "bssid": "cf:b8:ed:3c:01:02" } }

Avec ssid ou bssid, le capteur ne lance pas de scan pour trouver la cible : il n'utilise que ce que ses scans lui ont déjà appris. Une borne jamais vue est donc refusée, pas tentée à l'aveugle. Sans paramètre, au contraire, le scan est le but même de l'appel — la réponse met alors une à deux secondes de plus à arriver. La bascule elle-même emprunte dans tous les cas le chemin normal du firmware : c'est le même comportement que celui déclenché spontanément par la dégradation du signal.

Résultat :

{
  "from_bssid": "cf:b8:ed:3e:01:02",
  "from_rssi": -74,
  "bssid": "cf:b8:ed:3c:01:02",
  "rssi": -61,
  "channel": 6,
  "changed": true
}
ChampDescription
from_bssid / from_rssiBorne quittée et son dernier RSSI mesuré (dBm).
bssid / rssiBorne visée et son dernier RSSI mesuré (dBm).
channelCanal de la borne visée ; 0 si le capteur laisse le supplicant la chercher.
changedfalse = la borne demandée était déjà la borne courante, aucune bascule n'a eu lieu et les champs from_* répètent la borne conservée.

La réponse arrive dès que la demande d'association est partie, pas à la fin de la bascule : le lien est coupé pendant quelques secondes ensuite. Suivez la reprise sur network_infos.links du status du device (état, SSID, BSSID, RSSI du lien WiFi ; voir API - Temps réel).

🔀 Particularités du Maxi. Le Maxi répond lui aussi par les champs ci-dessus, avec en plus :

ChampDescription
statusDécision prise : roaming (bascule lancée), already_connected (déjà sur la borne demandée), scan_armed (cible pas encore visible : le capteur la cherche pendant quelques secondes, puis bascule), ou rejected (refus, voir plus bas). changed vaut true seulement pour roaming.
reasonPrécise le cas : avec scan_armed, target_not_seen (borne jamais vue) ou candidate_stale (vue, mais trop anciennement).
from_channelCanal de la borne quittée.
ssidSSID de la borne visée, quand elle est connue.
recently_failedtrue si la borne visée a refusé l'association récemment ; la bascule est tentée quand même, comme demandé.

Contrairement au Phyling-Live, le Maxi ne refuse donc pas une borne qu'il n'a pas encore vue (target_not_seen, scan_armed : succès, pas d'erreur) et n'a pas les refus not_associated, radio_busy ni scan_timeout. Ses erreurs s'ajoutent à celles du tableau ci-dessous : -32602 malformed_params (ssid ou bssid qui n'est pas une chaîne), -32602 malformed_ssid (ssid vide) et -32603 wifi_begin_refused (le pilote WiFi a refusé la demande d'association). Pour un refus, la réponse d'erreur porte dans error.data la même structure que le résultat (status: "rejected" et reason).

Erreurs possibles :

Chaque refus du device porte un error.data.reason (cf. « Codes d'erreur RPC » plus haut) qui précise laquelle des causes du code s'applique :

{
  "code": -32000,
  "message": "Service unavailable",
  "data": { "reason": "target_not_seen", "current_bssid": "cf:b8:ed:3e:01:02" }
}
CodereasonCause
-32601(aucun)Firmware sans wifi_connect (méthode non déclarée).
-32602ambiguous_targetssid et bssid fournis ensemble.
-32602malformed_bssidbssid qui n'est pas au format xx:xx:xx:xx:xx:xx.
-32602malformed_targetssid ou bssid fourni n'est pas une chaîne, ou ssid dépasse la longueur maximale acceptée.
-32602ssid_not_configuredssid qui ne correspond à aucun réseau activé de la configuration du device.
-32000target_not_seenLa borne visée n'est pas dans la table de voisinage (aucun scan ne l'a vue).
-32000not_associatedLe capteur n'est associé à aucune borne.
-32000radio_busyUne bascule ou un scan est déjà en cours.
-32000scan_timeoutLe scan demandé (appel sans paramètre) n'a pas abouti.
-32603switch_failedLe supplicant a refusé la demande d'association ; data.errno porte son code.
-32003(aucun)Timeout côté serveur (pas de réponse du device).

Sur target_not_seen et not_associated, data porte en plus current_bssid, la borne sur laquelle le capteur se trouve — absent si le lien est coupé et qu'il n'y en a aucune.

🔎 Distinguer les deux refus les plus courants. ssid_not_configured veut dire que ce réseau n'est pas (ou plus) activé dans le wifi.json du device — c'est un problème de configuration. target_not_seen veut dire que la cible est bien configurée mais que le capteur ne la voit pas — c'est un problème de couverture radio.

Lister les calibrations automatiques — v1.board.calib.auto.get

📡 Phyling-Live uniquement. Les autres devices ne déclarent pas cette commande : vérifiez la présence de la clé calib_auto dans features (voir API - Temps réel) avant de l'appeler, sinon la requête répond -32601.

Retourne la liste des calibrations que le capteur sait exécuter lui-même, sans intervention du serveur.

{ "method": "v1.board.calib.auto.get" }

Résultat :

{
  "calibrations": [
    {
      "module": "imu",
      "name": "gyro",
      "duration": 3,
      "title": { "fr": "Calibration gyro", "en": "Gyro calibration" },
      "description": { "fr": "Posez le capteur…", "en": "Place the sensor…" }
    }
  ]
}
ChampDescription
moduleNom de l'instance du module dans la configuration du device (pas son type). À réutiliser tel quel dans v1.board.calib.auto.start.
nameIdentifiant de la calibration, à réutiliser tel quel.
durationDurée de la mesure en secondes, propre à chaque calibration.
titleLibellé court localisé (fr / en), à afficher dans votre interface.
descriptionConsigne localisée à suivre avant de lancer la calibration (position du capteur, immobilité…).

Erreurs possibles : -32000, -32003, -32603 (échec interne côté device en listant les calibrations).

Lancer une calibration automatique — v1.board.calib.auto.start

📡 Phyling-Live uniquement. Même remarque que ci-dessus sur la clé calib_auto de features.

{
  "method": "v1.board.calib.auto.start",
  "params": {
    "module": "imu",
    "name": "gyro"
  }
}

module et name doivent provenir de v1.board.calib.auto.get.

Résultat :

{
  "set_status": {
    "state": "calibrating"
  }
}

La réponse arrive immédiatement, sans attendre la fin de la mesure. Le device passe alors à l'état calibrating (LED cyan) pendant duration secondes, puis enregistre le résultat et revient à idle. Suivez l'avancement sur le champ state du status du device.

Déroulé complet :

  1. Le device doit être à l'état idle ou en veille (idle_sleep, il est alors réveillé avant la mesure) : une calibration ne peut pas démarrer pendant un enregistrement.
  2. Affichez la description de la calibration et attendez que l'utilisateur ait placé le capteur.
  3. Envoyez la commande. Le capteur ne doit pas bouger tant qu'il n'est pas revenu à idle.
  4. À la fin, la nouvelle calibration est appliquée et publiée automatiquement ; v1.board.calib.get renvoie la version à jour.

⚠️ Si le capteur a bougé pendant la mesure, ou si le résultat sort des plages attendues, la calibration est rejetée : rien n'est enregistré, l'ancienne calibration reste en place et le device revient à idle. Recommencez sur un support stable.

Erreurs possibles : -32602 (module ou calibration inconnue), -32000 (module déconnecté), -32001 (device ni à l'état idle ni en veille, ou calibration déjà en cours), -32003.

Démarrer un enregistrement — v1.record.rec.start

{ "method": "v1.record.rec.start" }

Résultat :

{
  "set_status": {
    "state": "record",
    "maxiRecId": 42
  }
}

Un capteur en veille (idle_sleep) est réveillé puis lance l'enregistrement.

Erreurs possibles : -32000, -32001 (enregistrement déjà en cours), -32003.

Arrêter un enregistrement — v1.record.rec.stop

{
  "method": "v1.record.rec.stop",
  "params": { "force_stop": false }
}
  • force_stop: false (défaut) : le device passe en mode recovery (recovery_record) avant de s'arrêter complètement. À utiliser dans le cas nominal.
  • force_stop: true : le device saute le mode recovery et s'arrête immédiatement.

Résultat :

{
  "set_status": {
    "state": "idle"
  }
}

ou "state": "recovery_record" si le device est en recovery.

Erreurs possibles : -32000, -32002 (aucun enregistrement en cours), -32003.

Réglages à chaud (profile) — v1.board.profile.apply

📡 Maxi, Phyling-Live et app mobile, firmware 7.0.8 et suivants. La méthode doit figurer dans settings.features (clé profile) ; sinon la route …/profile répond 400.

💡 Choisir les valeurs. Pour composer une configuration adaptée à votre usage (réseau, niveaux de roaming, fréquences, consommation, délai des commandes), consultez la page Profils : réseau, roaming et fréquences.

Un réglage à chaud change une partie de la configuration du capteur pendant qu'il fonctionne, sans redémarrage et sans couper un enregistrement en cours : fréquences d'acquisition et de diffusion, cadence d'envoi, mise en pause d'un module ou d'un lien réseau, capteur BLE visé (bleName / bleAddr), et, sur Maxi et Phyling-Live, la veille et l'état du capteur (state). Contrairement à v1.board.config.set, la commande est acceptée dans tous les états (idle, enregistrement…).

Parcours type :

  1. Lisez les réglages modifiables et leurs règles : GET /devices/rt/{client_id}/{device_number}/profile (répétez l'appel tant que la réponse est 202).
  2. Modifiez les valeurs voulues dans l'objet profile.
  3. Envoyez-le avec POST …/rpc/request et la méthode v1.board.profile.apply ("persist": false pour un changement temporaire).
  4. Lisez le résultat avec POST …/rpc/response (voir plus haut).

1. Lire le profil :

curl -H "Authorization: ApiKey <key>" \
  https://api.app.phyling.fr/devices/rt/12/3042/profile
{
  "profile": {
    "config": {
      "modules": {
        "imu": { "paused": false, "rate": 100, "realtimeRate": 50, "realtimeLowRate": null },
        "pedalier": { "paused": false, "rate": 200, "realtimeRate": 50, "realtimeLowRate": null }
      },
      "sendingDelay": 0.1,
      "disconnect_timeout": 30,
      "low_rate_buffer_pct": 0
    },
    "wifi": { "roaming": { "level": 1 } }
  },
  "rules": {
    "config.modules.imu.rate": { "kind": "number", "editable": true, "hot": true, "zero": false, "integer": false, "max": 1666 },
    "config.modules.pedalier.rate": { "kind": "number", "editable": false, "hot": false, "zero": false, "integer": false, "max": 5000 },
    "config.modules.imu.paused": { "kind": "bool", "editable": true, "hot": true },
    "config.sendingDelay": { "kind": "number", "editable": true, "hot": true, "min": 0.1, "max": 120, "zero": true, "integer": false },
    "wifi.roaming.level": { "kind": "enum", "editable": true, "hot": true, "values": [0, 1, 2, 3] }
  }
}

La route est asynchrone :

  • 200 avec {"profile": …, "rules": …} quand le serveur connaît déjà la configuration et le wifi.json du capteur (cas courant). profile reprend le format de la commande (arbres config et wifi, valeurs nues) : vous pouvez le renvoyer tel quel ou après modification.
  • 202 avec l'en-tête Retry-After (en secondes) et le corps {"status": "pending"} : le serveur a demandé les fichiers au capteur. Rappelez la même URL après Retry-After, jusqu'au 200.
  • 504 : le capteur n'a pas répondu dans le délai. Ce délai dépend du capteur (un Phyling-Live en veille radio répond plus lentement) ; relancez simplement l'appel.
url=https://api.app.phyling.fr/devices/rt/12/3042/profile
while true; do
  code=$(curl -s -o profile.json -D headers.txt -w '%{http_code}' \
    -H "Authorization: ApiKey <key>" "$url")
  [ "$code" != "202" ] && break
  sleep "$(awk 'tolower($1)=="retry-after:" {print $2+0}' headers.txt)"
done
echo "HTTP $code"   # 200 : profile.json contient {profile, rules}

2. Appliquer un changement :

curl -X POST -H "Authorization: ApiKey <key>" -H "Content-Type: application/json" \
  https://api.app.phyling.fr/devices/rt/12/3042/rpc/request \
  -d '{"method": "v1.board.profile.apply",
       "params": {"persist": false,
                  "config": {"sendingDelay": 0.5,
                             "modules": {"imu": {"realtimeRate": 25}}}}}'

Seules les clés à modifier sont nécessaires, mais le profil renvoyé par la route profile peut aussi être renvoyé tel quel. Une valeur null n'est jamais transmise (ce n'est pas un changement). Sans "persist": true, le serveur réduit le patch aux valeurs qui changent réellement le profil (bleName et bleAddr sont toujours transmis, car renvoyer la même cible retire l'autre clé et relance la connexion). Si rien ne change, aucune commande n'est envoyée au device : la route répond 200 directement avec {"applied": {}, "ignored": []} et un id (que …/rpc/response sert aussi, comme une réponse de device). Avec "persist": true, le serveur ne retire que les valeurs identiques au profil et non modifiables à chaud (règle hot: false, comme la fréquence d'un Mini) : un réglage déjà appliqué sans persist est ainsi bien écrit dans la configuration du capteur, et la commande part toujours. Dans les autres cas, la route répond 201 avec un id à interroger sur …/rpc/response (voir plus haut).

Résultat :

{
  "applied": {
    "config": { "sendingDelay": 0.5, "modules": { "imu": { "realtimeRate": 25 } } }
  },
  "ignored": []
}
ChampDescription
appliedLes valeurs effectivement appliquées, dans la même arborescence que le patch.
ignoredChemins du patch ignorés car l'élément est absent du device (module non présent, lien réseau inexistant…). Ce n'est pas une erreur.
persistedPrésent seulement avec "persist": true : true si le changement a été écrit dans la configuration du capteur et survit à un redémarrage, false si l'écriture a échoué (le réglage reste appliqué jusqu'au prochain redémarrage).

Avec "persist": false, le réglage est perdu au redémarrage du capteur. Une mise en pause (paused) n'est jamais conservée au redémarrage.

Les règles (rules) :

rules donne, pour chaque réglage, une règle indexée par son chemin (config.modules.imu.rate, wifi.roaming.level…).

ChampDescription
kindType de valeur : number, bool, enum, ble (nom ou adresse d'un capteur BLE) ou text.
hottrue : modifiable à chaud. false : affiché pour information, à changer via la configuration complète.
editablefalse : la valeur ne peut pas être modifiée sur ce device.
min / maxBornes d'un nombre, dans l'unité de la clé (Hz pour une fréquence ; une durée …Delay prend les bornes inverses de sa fréquence). min absent : toute valeur strictement positive est acceptée.
zerotrue : la valeur 0 est acceptée en plus de la plage (par exemple 0 pour arrêter un flux).
integertrue : seules les valeurs entières sont acceptées.
valuesPour une énumération (enum), liste des valeurs permises.

wifi.roaming.level accepte 0, 1, 2 et 3. Le niveau 3 (« découverte ») est destiné aux parcours le long de routeurs jamais vus : il cherche et bascule le plus tôt, au prix de la consommation la plus forte. Le niveau configuré n'est appliqué que pendant un enregistrement : hors enregistrement, le niveau effectif est 0 (les rapports du capteur restent au niveau configuré). Détail des niveaux : Profils : réseau, roaming et fréquences.

Veille et état du capteur (Maxi et Phyling-Live) : le bloc config.idle_sleep règle la veille, à chaud et avec persist :

CléValeursDéfaut
config.idle_sleep.autotrue / false : veille automatiquetrue
config.idle_sleep.inactivity_minDurée sans activité avant la veille, entier de 1 à 1440 min30

La clé de premier niveau state demande un état cible : "idle" (réveille le capteur, ou arrête un enregistrement en cours), "idle_sleep" (met en veille, en arrêtant un enregistrement en cours) ou "record" (lance un enregistrement, en réveillant d'abord le capteur s'il dort). Elle n'est jamais persistée et s'applique après les autres réglages du patch (un enregistrement démarre donc avec les nouveaux réglages) ; applied.state reprend la cible. Un état déjà atteint est un succès sans effet. Dans le profil servi par la route …/profile, state vaut toujours null : renvoyer ce profil tel quel ne change pas l'état du capteur. L'app mobile n'a ni veille ni state (not_modifiable).

Exemple, réveiller le capteur et couper la veille automatique en un seul patch :

{"persist": true, "config": {"idle_sleep": {"auto": false}}, "state": "idle"}
{"applied": {"config": {"idle_sleep": {"auto": false}}, "state": "idle"}, "ignored": [], "persisted": true}

Une valeur de state inconnue est refusée en -32602 (path state, reason type ou out_of_range). Si l'état demandé n'est pas accessible au moment de la commande, rien n'est appliqué et la réponse est une erreur -32001 :

{"code": -32001, "message": "Record in progress", "data": {"path": "state", "reason": "busy"}}
reasonCause
busyLe capteur est dans un état transitoire (démarrage ou arrêt d'un enregistrement, calibration…), ou la veille est demandée pendant un envoi d'enregistrement (Maxi) : réessayez après.
refusedLa transition est refusée par le capteur.
unreachableAucun chemin vers l'état demandé depuis l'état actuel.

Une valeur null dans profile signifie que la clé n'est pas définie dans la configuration : le capteur applique sa valeur par défaut. Envoyer null n'est pas un changement.

Erreur -32602 : tout ou rien. Si une valeur du patch est refusée (clé non modifiable, hors bornes, mauvais type), rien n'est appliqué et la réponse contient la liste des refus :

{
  "code": -32602,
  "message": "Invalid params",
  "data": { "invalid": [ { "path": "config.modules.imu.rate", "reason": "out_of_range" } ] }
}
reasonCause
not_modifiableClé non modifiable à chaud sur ce device (voir hot / editable).
out_of_rangeValeur hors des bornes ou des valeurs permises.
typeType de valeur incorrect.
last_linkPhyling-Live en dual : mise en pause du dernier lien réseau actif, refusée pour ne pas couper le capteur.

Le firmware garde le dernier mot : il peut refuser une valeur que les rules acceptent si elle dépasse ses limites matérielles.
